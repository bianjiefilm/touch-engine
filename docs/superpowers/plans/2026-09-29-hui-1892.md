# 计划：HUI-1892 真实接收收口

- 日期：2026-09-29；票：HUI-1892；分支 `hui-1892-chain-close`
- 设计：`docs/superpowers/specs/2026-09-29-hui-1892-design.md`
- 测试一律 `GOWORK=off`。先改测试并看到失败，再改实现。

## 1. 定向事件客户端

`DirectedPoster.PostEvent` 改为返回 `(notifyEventID string, error)`。

失败测试：

- 完整信封发出后，正文是包装，`type` / `app_id` / `tenant_id` / `data` 对齐，返回的 id 来自响应 `event_id`。
- 2xx 但没有 `event_id` 是错误。
- `deliveries` 请求带 `app_id`，只解码 `deliveries`。只有 `items` 时得到空列表，不当成送达。
- 开关关闭或未配置时，仍在解析之前失败。

实现在 `server/internal/notifytask/directed.go`。不把联系方式写进包装。

## 2. 出站 id

迁移 `0017_leads_notify_event.sql`：`leads_outbox.notify_event_id TEXT NOT NULL DEFAULT ''`。

`MarkOutboxForwarded(eventID, notifyEventID)` 同时写下这个 id。`NotifyEventID(submissionRef, kind)` 读已转发的那一行。

转发器保存返回的 id。空 id 不标记已转发。确认阶段只用 submit 行上的 notify id；空则跳过，保持 `pending_sync`。

失败测试：`notifyStub` 要求包装，返回与 submission ref 不同的 `evt_*`，投递状态挂在这个 id 上，查询要 `app_id`，正文键是 `deliveries`。未知 id 返回空 `deliveries`。只有 `items` 的别名不能把线索写成 `crm_received`。快乐路径在确认后仍是 `crm_received`，并断言库里的 notify id。`store` 测试改传两个参数并读回 id。

## 3. 跟进摘要

`followUpSummaries` 在 `AppID` 非空时设置 `source_app`。

失败测试：`TestWorkbenchReadsFollowUpSummary` 要求 `source_app=touch-engine`。摘要失败时待跟进仍无 `value`。不改工作台组件和 `salesReceipt`。

## 4. 验收运行

代码变绿之后，在空闲端口启动本地身份桩、touch、以及 `/tmp` 里的 leads `origin/main` 副本和未改动的 platform-notify。浏览器走商家、访客、销售。证据放在 `evidence/hui-1892/`。销售界面做不到首次跟进时，报告写「销售工作台首次跟进未完成」。

## 5. 拒绝之后的送达和撤销

验收里第一次投递是 dead，线索被记成 `rejected`。同一条 notify 事件后来变成 `delivered` 时，确认要改写成 `crm_received`。仍是 dead 就保持拒绝。

失败测试：

- `TestRejectedDeliveryRepairsWhenSameEventIsDelivered`：dead 之后同一事件 delivered，状态变成 `crm_received`，同步错误清空。
- `TestRevokeLeadMatrix/rejected_after_forward` 和 `TestRevokeAfterRejectedEnqueuesStop`：已转发又被拒绝的提交仍能撤销，本地回到原租户，并排出 `lead.consent_revoked`。

`MarkLeadDelivered` 允许从 `rejected` 过来。确认阶段对 `rejected` 只接受 `delivered`。`RevokeLeadSubmission` 允许 `rejected`。
